# 短期云端迁移实施计划

> **执行要求：** 后续使用 `executing-plans` 按任务顺序实施。每个阶段完成后报告结果并等待用户确认下一步；服务器环境和手机访问由用户亲自验证。不使用并行代理，不额外开发通用验证平台。

**目标：** 让现有推荐控制台在腾讯云 Linux 服务器短期运行，并通过脚本完成本机到云端、云端到本机的单一写入端交接。

**架构：** 云端单个 FastAPI 进程只监听本机地址；Nginx 在独立的公网 `8081` 端口提供前端及 `/api`，用分设备 Basic Auth 认证。可移植的 Python 交接工具制作和校验 SQLite 快照及文件清单，Git Bash/SSH 脚本负责传输和切换。本机现有启动方式及 `8080` 记账应用不变。

**技术栈：** Python 3.11+、SQLite、FastAPI、React/Vite、Nginx、systemd、Git Bash、SSH/SCP。

**设计依据：** `docs/superpowers/specs/2026-09-28-短期云端迁移与数据交接设计.md`

## 全局约束

- 云端仅用于两三天，运行在现有 2 核 4 GiB Linux 服务器；不新增计算实例，不调整模型、信号、评分或建议手数规则。
- 使用 HTTP；不加入域名、TLS 或 Tailscale。每台设备一组独立用户名和 12 位密码，密码只用小写字母及数字 `2` 至 `9`，排除 `i`、`l`、`o`，并可单独撤销。HTTP 凭据在传输中不保密。
- Nginx 保护页面与全部 API；后端不得直接暴露公网；云端只启动一个后端 worker。本机访问继续免登录，既有 `8080` 应用保持不变。
- 本机与云端绝不同时写入同一份业务数据。发现训练、纸面自动任务或赔率 worker 仍运行时，交接应停止并报告，不擅自终止任务。
- `.env` 不入 Git、不入通用交接包、不出现在网页目录；仅通过 SSH 单独传送。不得覆盖用户现有工作区改动或在回迁时覆盖本机已变化的数据。
- 本机命令固定使用 `C:\ProgramData\anaconda3\python.exe`，并设置 `PYTHONPATH=src`、`PYTHONIOENCODING=utf-8`。每次代码提交只暂存本任务文件，提交信息使用中文。

## 文件分工

- `src/icewine_prediction/artifact_path.py`：解析数据库中跨系统的相对训练产物路径；现有推荐服务和 CLI 调用它。
- `web/src/apiClient.ts`：生产构建的 API 失败提示；开发环境保留现有 mock 回退。
- `src/icewine_prediction/cloud_handoff.py`：SQLite 快照、文件选择、SHA-256 清单、校验和本机恢复；`scripts/cloud_handoff.py` 仅提供命令行入口。
- `scripts/cloud_upload.sh`、`scripts/cloud_return.sh`：Windows Git Bash 侧经 SSH/SCP 传输和阶段切换，不在命令行暴露密钥。
- `deploy/cloud/icewine.service.template`、`deploy/cloud/nginx.conf.template`、`scripts/cloud/setup.sh`、`scripts/cloud/manage_credentials.py`：云端独立服务、Nginx 入口及设备凭据管理。
- `tests/test_artifact_path.py`、`tests/test_cloud_handoff.py`、`web/src/apiClient.test.ts`：只覆盖跨系统路径、数据校验/覆盖拒绝和生产环境不显示 mock 这几项高风险行为。

## 重点验收条件

| 条件 | 处理阶段 | 验收方式 |
| --- | --- | --- |
| Linux 读取数据库内 Windows 反斜杠路径 | 任务 2 | 小型路径单测及一次真实推荐 |
| 云端 API 失败时显示假比赛 | 任务 2 | 前端单测和手机断开后端实测 |
| 文件传输中断、哈希不符或清单含越界路径 | 任务 3 | 小型临时库测试；脚本拒绝覆盖 |

| 新入口绕过认证或影响 `8080` | 任务 4、6 | 用户现场用手机及服务器命令核对 |

## 任务 1：收集云端环境信息

**产出：** 明确服务器可用的发行版、端口、磁盘及运行条件。本任务不改代码、不改云服务器配置。

- [ ] 用户在服务器执行 `cat /etc/os-release`、`uname -m`、`free -h`、`df -h`、`ss -lntp`、`python3 --version`，并确认腾讯云安全组当前规则。分享结果时隐藏公网登录凭据和密钥。
- [ ] 我根据结果确定 Python 安装方式、后端本地端口和 Nginx `8081` 是否可用；若可用磁盘不足 15 GiB，先缩小备份保留或处理磁盘，不开始上传。
- [ ] **暂停点：** 用户确认现有 `8080` 应用正常、可接受 `8081` 作为新入口，且环境信息已核对。后续脚本依据该结果选择安装命令。

## 任务 3：实现数据快照、清单和恢复工具

**文件：** 新增 `src/icewine_prediction/cloud_handoff.py`、`scripts/cloud_handoff.py`、`tests/test_cloud_handoff.py`。暂存目录使用 Git 忽略的 `.web/cloud-handoff/`。

**接口：** `prepare_initial(project_root: Path, output_dir: Path) -> Path`、`prepare_return(project_root: Path, output_dir: Path, initial_manifest: Path) -> Path`、`verify_bundle(bundle_dir: Path) -> None`、`restore_return(project_root: Path, bundle_dir: Path, initial_manifest: Path) -> None`。命令行分别暴露 `prepare-initial`、`prepare-return`、`verify`、`restore-return`。

- [ ] 用临时 SQLite 库增加少量失败先行测试：备份可重新打开；清单能选中最近一次成功训练而非固定日期；篡改文件或越界路径时校验失败；本机主库哈希变化时恢复拒绝覆盖。
- [ ] 实现 SQLite `backup` 和 `integrity_check`、按清单选取代码/前端/运行数据、SHA-256 校验以及保留旧文件的恢复流程。首次包不含 `.env`、历史数据库副本和开发缓存；回迁包包含云端主库、训练/报告新文件、可写 YAML 和相关日志。初次交接清单在本机和云端各留一份。
- [ ] 运行 `C:\ProgramData\anaconda3\python.exe -m pytest tests/test_cloud_handoff.py -q`；再只用临时目录演练一次 `prepare-initial → verify → prepare-return → restore-return`，不触碰真实主库。
- [ ] 只提交本任务文件，中文提交信息。**暂停点：** 向用户报告按当时最新训练记录计算的实际待上传大小和文件类别，由用户确认范围。

## 任务 4：准备云端运行配置和简易设备凭据

**文件：** 新增 `deploy/cloud/icewine.service.template`、`deploy/cloud/nginx.conf.template`、`scripts/cloud/setup.sh`、`scripts/cloud/manage_credentials.py`；按任务 1 的发行版结果补充对应命令到部署说明。

**接口：** `setup.sh` 只安装/配置独立的 Icewine 服务，不改动现有 `8080`；`manage_credentials.py add <设备名>` 交互生成并显示一次 12 位密码，`remove <设备名>` 撤销账号。密码经标准输入交给 `htpasswd`，仓库和命令行参数不保存明文。

- [ ] 实现 Nginx 静态目录及 `/api` 代理统一 Basic Auth、localhost 后端、单 worker 的 systemd 模板。`.env` 和哈希凭据文件放在网页目录外且权限受限。
- [ ] 本地检查生成的凭据长度及字符集，检查配置模板不含真实密钥；云端安装时由用户运行 `nginx -t`、`systemctl status`，并确认 `8080` 仍可用。这里不开发额外的认证测试平台。
- [ ] 只提交本任务文件，中文提交信息。**暂停点：** 用户审看设备名、密码输入体验及服务器服务配置，再进入真实部署。

## 任务 5：编写并演练传输脚本

**文件：** 新增 `scripts/cloud_upload.sh`、`scripts/cloud_return.sh`；必要时补充 `scripts/cloud/setup.sh` 的激活命令说明。

- [ ] `cloud_upload.sh` 先检查本机 Web 与独立 worker 状态，再调用任务 3 制作快照；若存在活动任务，只报告并停止。经 SCP 上传通用包，`.env` 单独通过 SSH/SCP 传送。云端先校验文件，再执行任务 4 的配置与启动。脚本不删除本机原库。
- [ ] `cloud_return.sh` 在云端任务结束且服务停止后，远程制作最终包并下载；先验证清单与本机初次交接哈希，再保留本机旧库并恢复数据。任何失败都停在原数据仍可用的阶段，不自动关闭云端副本。
- [ ] 用临时小文件及测试目录演练传输脚本参数和失败退出；不对真实服务器执行切换。只提交脚本，中文提交信息。
- [ ] **暂停点：** 向用户展示上传、回迁命令及失败退出方式。用户审阅脚本和数据范围后，再安排首次真实切换。

## 任务 6：首次真实切换

- [ ] 用户确认本机活动任务均已结束，云端磁盘空间、端口和安全组就绪；执行上传前再次检查本机写入状态。若条件不满足，只报告原因并停止。
- [ ] 执行或指导执行首次上传、云端校验、独立服务安装及启动。用户亲自验证未认证请求、每组设备凭据、后端公网不可访问、手机和电脑上的比赛、赔率、推荐及训练页面，并检查原有 `8080` 应用。
- [ ] 用同一数据库和训练 CSV 核对一条云端推荐结果。用户确认业务结果后，将云端设为唯一写入端，本机保持停止。**暂停点：** 记录已验证的版本、数据清单和云端状态；短期使用期间不自动回迁。

## 任务 7：短期运行与回迁

- [ ] 云端每天用任务 3 的快照能力留一份数据库备份并限制保留份数；只查看磁盘余量、服务状态和必要日志，不加复杂监控系统。完整训练先在 4 GiB 机器上实测，避免与批量回填并行。
- [ ] 回迁当天由用户确认云端任务和 worker 已结束、可以暂停访问；再执行 `cloud_return.sh`。检查本机最近的比赛、赔率、训练文件及推荐记录，并由用户完成手机/本机业务验收。
- [ ] 用户确认本机恢复后，关闭云端 `8081` 和 Icewine 服务，保留最终云端备份至双方确认无需回退。**最终完成条件：** 本机是唯一写入端，云端入口关闭，现有 `8080` 应用仍正常。

## 实施顺序说明

任务 1 是环境信息确认；任务 2 至任务 5 可在不切换真实业务数据的情况下逐步完成；任务 6 才发生首次真实切换；任务 7 留到实际结束云端使用时执行。每项完成后先展示结果并停在其暂停点，按用户的现场验证结果调整下一步。代码验证保持聚焦，服务器发行版、端口、网络、手机界面和业务数据由用户亲自验收。
